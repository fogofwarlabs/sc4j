# Beacon.Link 프로토콜 참조, 프로토콜 1

[English](protocol.md) | **한국어**

Beacon.Link의 와이어 형식과 파일: 피어와 클라이언트의 메시지(`sc4j-beaconlink-protocol`), 수신 규칙(`sc4j-beaconlink-peer`, `MeshPeer`), 참가자 사이의 채널(`sc4j-beaconlink`). 모든 SC4J가 피어를 실행하며(런처의 노드, 런타임의 내장 피어, [운영 가이드](operator.ko.md)의 헤드리스 노드), 중앙 서버는 없습니다. 세부 규범은 이름이 나온 클래스의 Javadoc입니다.

따로 적지 않으면 정수는 빅 엔디언, 부호 없음입니다. 데이터그램은 최대 1200바이트입니다. 텍스트는 1바이트 길이가 붙은 UTF-8이며, 잘못된 UTF-8은 거부합니다. 주소는 패밀리(1바이트, `4` 또는 `6`), 4 또는 16바이트 주소, 포트(2)이며, 읽는 동안 이름을 조회하지 않습니다. 읽는 쪽은 잘린 필드, 범위 밖 값, 남는 바이트를 예외 없이 거부합니다.

## 정체성

- **키**: Ed25519(JDK). 32바이트 공개 키가 정체성이며, 새 키는 새 정체성입니다. 플레이어 키(`accounts/<id>/identity.key`, 런처가 계정과 함께 만듦)는 방, 접속 상태, 채팅 줄, 귓속말, 신호에 서명하고 `Name#abcd12`(이름과 키 SHA-256의 앞 16진수 6자리, `IdentityKey.getTag`)로 보입니다. 피어 키는 라우팅 전용이며 보이지 않습니다: 런처 노드의 `peer.key`, 헤드리스 노드의 `<state>/identity.key`, 런타임 실행의 내장 피어는 메모리의 키. 처음 쓸 때 만들어집니다.
- **키 파일**(`IdentityKeyFileUtils`): 매직 `BLKF`, 버전 `1`, 개인 키 바이트, 공개 키 바이트. 폴더의 임시 파일을 거쳐 원자적으로 씁니다(POSIX에서는 `rw-------`, 교체된 파일도 유지).
- **연결**: 클라이언트 세션은 수명 동안 쓰는 무작위 연결 번호(8바이트)를 뽑고, 시작한 에포크 밀리초가 연결 시작입니다. 참가자(`LinkParticipant`, 와이어 형식은 키 32 + 번호 8)는 플레이어 키 + 연결 번호입니다. 등록, 방, 신호, 채널, 오버레이, 로비, 락스텝 전송은 참가자를 가리키므로, 계정 하나의 연결들이 서로를 포함해 나란히 동작합니다. 친구, 접속 상태, 채팅 줄, 귓속말, 무시 목록은 플레이어(`LinkPlayer`) 단위입니다. 어느 연결이든 등록하려면 플레이어 키와 스탬프가 필요합니다.
- **플레이어 이름**(`PlayerNameUtils`): Unicode NFC, 앞뒤 공백 없음, 안의 연속 공백은 공백 하나. UTF-8 1~32바이트. `#`, 제어, 서식, 사용자 정의, 서로게이트, 미할당 문자 없음. 올바른 이름은 자기 정규형입니다. 스탬프가 이름을 키에 묶으므로 다른 이름은 다른 계정입니다.
- **계정**(`AccountStore`, `Account`): 계정마다 id(키 SHA-256의 앞 16진수 16자리) 이름의 폴더 하나이며, 키, 이름, 플레이어 스탬프, 친구, 무시한 플레이어가 있습니다. 사용자가 계정을 만들거나(이름, 무작위 키, 스탬프) 가져오고, 게임이 쓸 계정을 고릅니다(`--account <dir>`). 이름 변경은 없습니다. 계정을 쓰는 모든 프로세스는 잠금 파일의 공유 잠금을 잡고(`AccountLock`), 삭제는 배타 잠금을 잡습니다. 계정 없는 실행은 메모리의 키와 스탬프를 가진 게스트 `Guest`입니다.
- **계정 백업**(`AccountBackup`, `.sc4jaccount`): 매직 `BLKA`, 버전 `1`, 플래그(비트 0: 비밀번호), 보호된 백업이면 솔트(16), PBKDF2-HMAC-SHA256 반복 횟수(4), AES-GCM nonce(12), 그 뒤 본문(이름, 스탬프 난이도(1), 스탬프 nonce(8), 키 파일, 친구, 무시한 플레이어). 보호된 백업의 본문은 헤더를 연관 데이터로 하여 비밀번호의 키로 AES-256-GCM 암호화합니다. 스탬프가 이름을 키에 묶지 않는 백업과 다른 모든 파일은 거부합니다.
- **게임 명령줄**: 실행은 `--account <dir>`(없으면 게스트), `--seeds <file>`(노드 목록), `--seed <host:port>`(반복 가능), `--peers <file>`(공유 피어 파일. 없으면 학습한 피어를 읽지도 남기지도 않음)에서만 Beacon.Link 설정을 받고, 뒤의 셋 중 하나가 있을 때만 제공합니다. 런처는 계정 폴더, 시드 규칙에 따른 시드(저장된 사용자의 `nodes.json`, 없으면 함께 배포된 `seeds.json`), 설치본의 `peers.json`을 넘깁니다. 실행의 내장 피어는 리프입니다. 런처의 노드는 이 컴퓨터의 오래 사는 피어이며, 설치본에서 처음 연 런처가 `node.lock`을 잡고 `peer.key`로 실행합니다. 다른 런처는 첫 런처가 닫힌 뒤 넘겨받습니다.
- **피어 ID**(`PeerId`): `BLNK peer id 1`, 피어 키, 증명 nonce(8)의 SHA-256. `BLNK peer proof 1`, 키, nonce의 SHA-256이 0 비트 20개로 시작하면 nonce가 유효합니다(네트워크의 난이도). 피어는 시작할 때마다 가장 작은 유효 nonce를 찾습니다. 받는 쪽은 ID를 쓰기 전에 증명을 확인합니다. ID는 XOR 거리로 비교합니다(Kademlia).
- **플레이어 스탬프**(`PlayerStamp`): `BLNK player stamp 1`, 플레이어 키, 이름의 UTF-8 길이(1), 이름, nonce(8)의 SHA-256이 0 비트 24개로 시작하게 하는 nonce이며, 이름은 올바른 이름이어야 합니다. 런처가 계정을 만들 때 한 번 찾아 `account.json`에 보관합니다. 등록, 접속 상태, 채팅 줄은 이름과 nonce를 담고, 스탬프가 묶지 않은 이름은 거부됩니다.

## 역할

- **전체 피어**: 자체 시험으로 모르는 상대가 소켓에 닿는다는 것이 증명된 피어. 전체 피어만 라우팅 테이블, `PEERS` 응답, 토픽의 저장 피어, `peers.json`에 들어가고, 토픽 알림을 저장하며 토픽 메시를 이룹니다.
- **리프**: 자체 시험 결과가 `NOT_VERIFIED` 또는 `NOT_REACHABLE`. 다른 피어처럼 조회하고 인사하고 답하며, 라우팅 테이블 밖에서 알려지고, 나중의 시험이 증명하면 승격합니다.
- **리프 전용**(`PeerConfiguration.isLeafOnly`): 전체 피어가 되지 않고, 카드는 항상 도달 불가이며 다이얼백을 요청하지 않지만, 다른 피어의 자체 시험에 도우미와 제3 피어로 응합니다. 끔 역할의 런처 노드입니다.
- **홈 피어**: 클라이언트 연결이 등록한 피어(`REGISTER`. 최대 3개, 클라이언트가 처음 등록한 노드). 관찰된 주소를 알려 주고, 클라이언트의 토픽에 참여해 레코드를 보내 주며, 등록된 연결로 신호와 귓속말을 중계합니다. 런타임 세션은 시드와 학습한 노드의 클라이언트이고 같은 소켓에 내장 리프를 실행합니다. 런처의 노드와 헤드리스 노드는 자기 소켓에서 단독으로 실행됩니다(`PeerSocket`, `PeerBootstrap.run`).
- **참가자**: 방에 있는 플레이어의 연결 하나. 게임 트래픽은 참가자 사이의 채널로만 흐릅니다.

## 엔벨로프 (`Envelope`, `MessageEncoder`)

| 필드 | 바이트 | 의미 |
|---|---|---|
| 매직 | 4 | `BLNK` |
| 버전 | 1 | `1` |
| 종류 | 1 | 메시지 종류 코드(아래) |
| 플래그 | 1 | 비트 0: 응답(응답에는 답하지 않음). 다른 비트는 0 |
| 요청 번호 | 4 | 요청자가 정하고 응답이 되풀이함 |
| 타임스탬프 | 8 | 보낸 쪽 벽시계, 에포크 밀리초(부호 있는 64비트) |
| nonce | 8 | 메시지마다, 재전송마다 무작위 |
| 보낸 쪽 키 | 32 | 보낸 쪽의 Ed25519 공개 키 |
| 본문 길이 | 2 | |
| 본문 | n | 종류별 |
| 패딩 길이 | 2 | |
| 패딩 | p | 0 바이트 |
| 서명 | 64 | 앞의 모든 바이트에 대한 보낸 쪽의 Ed25519 서명 |

헤더는 61바이트, 트레일러는 `2 + p + 64`입니다. 엔벨로프는 받는 쪽을 밝히지 않으므로 서명된 데이터그램은 어느 피어에서나 유효합니다. nonce 확인이 키 속도보다 먼저이고, 벌점은 증명된 주소일 때만 키 단독이나 주소 단독을 그레이리스트에 올립니다([수신](#수신)).

**요청 번호**: 피어 계층은 무작위(아직 기다리는 번호는 제외), 토픽 계층, 자체 시험, 클라이언트는 무작위 시작값부터 하나씩 셉니다. 응답은 기다리는 번호를 가지고, 요청한 주소에서 왔으며, 알고 있다면 예상한 키일 때만 받습니다.

**패딩**: 증명되지 않은 주소로 가는 요청(`PING`, `REGISTER`, `HELLO`, `DIAL_BACK`)은 256바이트, `FIND_PEERS`는 617바이트(가장 긴 `PEERS`), `GET_TOPIC`은 1155바이트(가장 긴 `TOPIC_PEERS`)로 패딩합니다. 피어는 증명되지 않은 주소에 요청보다 긴 응답을 보내지 않으며, 그런 응답은 보내지 않고 셉니다(`UNPADDED`). 거부도 마찬가지입니다(`PUBLISH_ROOM`, `LIST_ROOMS`, `SIGNAL`, `PUBLISH_RECORD`, `RECENT`에 대한 `NOT_REGISTERED`, `ANNOUNCE`, `GRAFT`에 대한 `INVALID`).

## 수신

### 피어에서 (`MeshPeer.receive`)

이 순서로 확인하며, 실패하면 버리고 세며 답하지 않습니다.

1. 길이 최대 1200바이트(`OVERSIZE`).
2. 출발지 IP 속도: 순간 256, 그 뒤 초당 128(`ADDRESS_RATE`).
3. 주소 그레이리스트(`GRAYLISTED`).
4. 엔벨로프와 본문 구조(`MALFORMED`), 클라이언트만 받는 응답 `OBSERVED_ADDRESS`, `ROOM_LIST`(`UNEXPECTED_REPLY`), 자기 키(`OWN_KEY`).
5. 받는 쪽 시계의 30초 안의 타임스탬프(`OUTSIDE_WINDOW`).
6. 서명(`FORGED`).
7. 키, 그리고 주소별 키의 그레이리스트(`GRAYLISTED`).
8. nonce: (보낸 쪽 키, nonce)를 창의 두 배 동안 기억, 전체 65536개, 출발지 IP당 최대 2048개. 가득 차면 새 메시지를 거부합니다(`REPLAYED`, `REPLAY_SOURCE_FULL`, `REPLAY_CACHE_FULL`).
9. 보낸 쪽 키 속도: 순간 32, 그 뒤 초당 16(`KEY_RATE`). 새롭고 올바르게 서명된 메시지에만 매깁니다.

처리기는 쓰지 않은 것을 셉니다: `UNPADDED`, `NOT_A_PEER`(그 주소에서 알려진 피어가 보내지 않은 피어 메시지, 또는 기다리는 요청이 없는 응답), `INVALID_PROOF`, `INVALID_ENTRY`(쓰지 않은 `PEERS`나 `TOPIC_PEERS` 항목마다), `UNREQUESTED_PROBE`, `NOT_IN_TOPIC`, `INVALID_RECORD`(레코드마다), `COORDINATE_OUTLIER`(표본마다). 예외를 던진 처리기는 데이터그램을 잃고 예외를 로그에 남기며 `DEFECT`로 셉니다. 카운트는 멈출 때(헤드리스 노드는 한 시간마다도) 로그에 남습니다.

### 벌점과 그레이리스트 (`Graylist`)

| 벌점 | 점수 |
|---|---|
| 잘못된 레코드: 다른 토픽이나 그곳에 속하지 않는 종류, 잘못된 서명이나 스탬프, 너무 긴 수명 | 10 |
| 위조된 증명을 가진 카드 | 10 |
| 작성자 속도를 넘은 레코드 | 2 |
| 만료된 레코드, 토픽 메시 밖 피어의 토픽 메시지, 요청 없는 응답, 패딩 없는 요청, 안정된 좌표가 거부한 좌표 표본 | 1 |

점수는 키와 출발지 주소별로 세고, 마지막 벌점 60초 뒤에 잊습니다. 40점이면 그 주소의 그 키를 10분 동안 그레이리스트에 올립니다. 주소가 그 키에 대해 증명되었으면(토큰으로 graft한 메시 이웃, 그 주소에서 답한 라우팅 연락처, 등록한 클라이언트) 키 단독과 주소 단독(IP 주소, 모든 포트. 루프백에서는 소켓 주소)도 올립니다. 그 데이터그램은 서명 확인 전(주소)이나 직후(키)에 버리고, 그 피어는 모든 메시, 멤버 목록, 저장된 알림에서 빠집니다. 벌점과 그레이리스트는 로컬입니다.

### 클라이언트에서 (`BeaconLinkClient`)

세션 소켓은 채널 데이터그램(매직 `BLCH`)과 엔벨로프를 나릅니다. 내장 피어가 있으면 세션은 기다리는 세션 요청(그 노드에서 온 것)이나 자기 귓속말에 대한 응답, 자기 노드에서 온 세션 키 앞의 신호나 귓속말, 피어가 참여하지 않는 토픽에 대한 노드의 푸시만 가지고, 나머지는 피어가 받습니다. 세션이 받는 것:

- 응답: 기다리는 번호, 요청한 노드에서, 창 안, 올바른 서명, 노드의 키(고정된 키, 또는 세션에서 그 노드의 첫 응답의 키. 다른 키면 노드가 잘못된 키로 답한다고 표시), 새 nonce.
- 신호: 등록한 노드에서, 자기 키와 연결 앞으로, 자기 참가자가 보낸 것이 아님, 창 안, 올바른 서명. 가지고 있거나 기다리는 채널의 신호와 가진 방의 참가만 처리하고, 재전송 방지를 위해 보낸 쪽 키별로 기억합니다.
- 푸시(`GOSSIP`, `IHAVE`, `SEALED`): 등록한 노드에서, 노드의 키(귓속말은 보낸 사람의 키), 창 안, 올바른 서명. 레코드는 중계자처럼 확인하고, 귓속말의 nonce는 보낸 사람별로 기억합니다.

실패는 버리고 출발지별로 셉니다. 결함은 로그에 남기고 폴링을 계속합니다.

## 메시지 종류 (`MessageKind`)

| 코드 | 종류 | 방향 | 본문 |

## 등록과 관찰된 주소

- 주소에서 온 첫 `REGISTER`에는 토큰이 없으며, 응답은 16바이트 토큰(실행별 비밀로 주소, 포트, 키를 HMAC-SHA256, 60초 구간 두 개 동안 유효)이 있는 `TOKEN_REQUIRED`입니다. 토큰을 담은 `REGISTER`가 관찰된 주소에 연결을 등록합니다(최대 4096개, 최대 300초). 등록된 주소에서 오는 갱신에는 토큰이 필요 없습니다.
- 표시 이름과 스탬프 nonce가 피어의 난이도에서 그 키의 올바른 스탬프가 아닌 증명된 `REGISTER`나 갱신은 `INVALID_NAME`으로 거부합니다.
- 등록된 연결만 게시, 목록, 구독, 신호를 할 수 있습니다(`FIND_PEERS`와 `SEALED`는 길이 규칙 안에서 누구에게나 답함). 큰 응답은 등록된 주소로만 갑니다. 클라이언트는 허용 수명의 절반마다 갱신합니다. NAT 재매핑은 `TOKEN_REQUIRED`로 나타나고 클라이언트는 다시 등록합니다.
- **연결**(`RegistrationStore`): (키, 연결 번호)마다 등록 하나, 키당 살아 있는 연결 최대 8개. 그 이상의 연결은 `TOO_MANY_CONNECTIONS`를 받으므로(만료된 연결이 먼저 자리를 내줌) 비정상 종료한 세션의 자리는 300초 안에 비워집니다. 같은 연결이 새 주소에서 오면 옮깁니다. 같은 키의 다른 연결의 주소에서 등록하는 연결은 그 연결을 대신합니다(주소 하나는 소켓 하나). 등록된 주소에서 온 수명 `0`은 그 연결만 지웁니다.
- 등록이 필요한 요청은 보낸 쪽 키의 어느 등록된 연결의 주소에서 와도 받고, 그 연결로서 동작합니다. 게시하는 방은 그 연결을 밝혀야 하고(아니면 `INVALID`), 구독은 연결마다 따로이며, 신호나 귓속말은 대상 연결을 밝히고 그 연결만 받습니다.
- `REGISTER`는 연결 시작을 담습니다. 그 키의 로그아웃([커뮤니티](#커뮤니티-presencerecord-chatlinerecord-signoutrecord-sealedmessage))을 가진 피어는 유지할 연결이 아니면서 로그아웃의 타임스탬프보다 먼저 시작한 연결을 `SIGNED_OUT`으로 거부하고, 그런 등록을 지우며, 로그아웃을 받아들일 때 모두 버립니다. 그 클라이언트는 어디에도 다시 등록하지 않습니다.
- 클라이언트는 무작위 대상의 패딩된 `FIND_PEERS`(카드 없음)로 노드에게 다른 노드를 묻고 공유 피어 파일([파일](#파일))에 기록합니다. 모든 노드에 첫 등록 뒤 한 번, 그리고 학습한 피어가 8개보다 적은 동안 목록의 노드에 마지막 응답 30초 뒤부터 간격을 두 배씩 늘리며 세션당 최대 8번 다시 묻습니다.
- **연결성**(`LinkConnectivity`, `BeaconLinkSession.getConnectivity()`): 클라이언트는 등록된 노드가 관찰한 공인 주소를 비교합니다(로컬 네트워크와 루프백 주소는 비교하지 않음). 포트 매핑이 있고 관찰된 공인 주소가 하나 이상이면 `OPEN`입니다. 그렇지 않으면 관찰된 공인 주소 두 개 이상이 포트 하나를 같이 쓸 때 `DIRECT`, 포트가 다를 때 `RESTRICTED`입니다(목적지마다 다른 포트를 주는 NAT로, 직접 채널이 실패하기 쉬움). 그 전과 포트 매핑을 아직 요청하는 동안은 `UNKNOWN`입니다. 정해진 값은 등록된 노드가 적어져도 유지되며, 클라이언트는 처음 정해진 값과 바뀔 때마다 로그를 남깁니다.

## 피어 계층 (`PeerRouting`, `RoutingTable`, `PeerLookup`)

**증명**: 피어는 시드, 후보(증명되지 않은 주소에서 hello나 조회 요청을 보낸 쪽), 기억한 피어, 조용한 아는 피어에게 5초 라운드마다 두 개씩 패딩된 `HELLO` 요청으로 인사합니다. 인사한 주소에서 온 응답이 주소와 키를 증명하며, `FIND_PEERS`에 대한 응답도 마찬가지입니다. 키 없는 시드는 기다리는 무작위 요청 번호를 담아 그 주소에서 온 첫 올바른 서명 응답을 믿고, 키가 고정된 시드는 아는 피어처럼 인사합니다. 모든 카드와 `PEERS` 항목의 증명을 확인하며, 항목은 답한 피어와 같은 종류(공인, 또는 로컬 네트워크와 루프백)의 IPv4 주소일 때만 씁니다.

**라우팅 테이블**: ID 공통 접두사에 따른 Kademlia k-버킷, 버킷당 피어 8개, 버킷당 증명된 피어 4개의 교체 캐시. 카드가 도달 가능이라고 하는 피어만 들어갑니다. 한계: 버킷당 같은 IPv4 /24(IPv6 /48) 2개, 테이블당 같은 /24 8개, 같은 IPv4 /16(IPv6 /32) 16개. 루프백은 제한 없음. 가득 찬 버킷은 기존 피어를 유지하고, 연속 2번 답하지 않은 피어(조회, 또는 10분 침묵 뒤의 hello)는 빠지며 한계 안의 가장 새로운 캐시 피어가 대신합니다. 증명된 리프와 자리가 없는 전체 피어는 테이블 밖에서 알려집니다(최대 256개, 60초 침묵이면 버림). 자체 시험이 쓰고, 테이블이 빈 동안 토픽 계층도 쓰며, `FIND_PEERS`에 답하거나 기억하지 않습니다.

**조회**: 반복 조회, 경로당 동시 요청 3개, 경로에서 가장 가까운 8개가 답하거나 실패할 때까지(요청당 2초와 재전송 1번, 조회당 30초, 동시 조회 최대 8개). 소유자의 조회(`MeshPeer.findPeers`)는 기본으로 서로 겹치지 않는 경로 3개를 씁니다. 시작 피어는 차례로 나눠 주고, 응답이 알려 준 피어는 다른 경로가 이미 알지 않으면 물은 경로에만 들어가며, 경로는 같은 /16의 피어를 최대 2개만 씁니다. 피어는 테이블에 피어가 생기고 첫 자체 시험이 끝나면 자기 ID를 조회하고, 자체 시험이 도달 가능을 증명하면 다시(요청의 도달 가능 플래그로 물은 피어가 자신을 테이블에 넣음), 테이블의 피어가 8개보다 적은 동안 30초마다, 그 밖에는 10분마다 무작위 버킷을 갱신합니다.

**부트스트랩**(`PeerBootstrap`, `KnownNodes`): 시드(시드 규칙, 노드의 `--peer` 옵션, 실행의 `--seeds`와 `--seed`)와 가장 좋은 학습한 피어 32개(`peers.json`: 최근 성공 순, 그다음 오래 알려진 순, 먼저 /24당 최대 2개)에 함께 인사하며, 먼저 답한 쪽으로 연결합니다. 라우팅 테이블의 전체 피어는 5분마다와 멈출 때 `peers.json`에 병합합니다. 런타임 세션은 자기를 등록한 노드, 내장 피어의 전체 피어, 목록의 노드가 알려 준 노드를 기록합니다. 학습한 피어는 연속 3번의 시작에서 시도했는데 답하지 않으면, 그 주소에서 다른 키가 답하면, 마지막 성공 30일 뒤에 버립니다.

## 도달성 자체 시험 (`ReachabilityCheck`)

- 피어는 무작위로 고른 아는 피어(도우미) 최대 둘에게 핑처럼 패딩한 `DIAL_BACK`을 요청합니다. 도우미는 카드 증명이 올바른 요청자만 돕습니다. 요청자의 관찰된 주소를 담아 무작위 제3의 아는 피어에게 전달하고 그 주소로 답하며, 제3 피어를 모르면 주소 없이 답합니다.
- 제3 피어는 증명된 주소에서 알려진 도우미만 돕고, 지정된 주소로 `PROBE`를 보냅니다(동시에 최대 4개, 그 뒤 IP 주소당 초당 1).
- 기다리는 다이얼백의 프로브나 패딩된 `HELLO` 요청이 소켓이 보낸 적 없는 주소(IP 기준, 루프백은 포트 기준. 주소 최대 4096개를 10분 기억)에서 오면 요청자는 도달 가능(전체 피어)입니다. 받아들여진 다이얼백의 프로브가 10초 안에 오지 않으면, 나중의 시험이나 요청 없는 hello가 증명할 때까지 리프입니다.
- 도달 가능은 유지합니다. 다른 결과는 받아들여진 시험 5분 뒤, 받아 준 도우미가 없거나 프로브가 보낸 적 있는 주소에서 왔으면 30초 뒤에 다시 시험합니다. 리프 전용 피어는 요청하지 않습니다.
- 출발지를 위조하면 요청 하나로 두 호스트가 피해자에게 보내게 할 수 있습니다(요청 바이트의 약 1.1배).

## 토픽 (`TopicKey`, `TopicSwarms`, `TopicDirectory`, `Swarm`)

**토픽 키**: 종류(1: `1` MOD, `2` CHANNEL, `3` PLAYER)와 `BLNK topic 1\0`, 종류 코드, UTF-8 이름의 SHA-256. 이름은 모드 id(모든 버전이 공유), 공백을 정리하고 소문자로 바꾼 최대 32바이트 채널 이름(모든 모드가 공유), 16진수 플레이어 키입니다. 해시에 가장 가까운 전체 피어가 저장 피어입니다. 피어는 소유자나 등록한 클라이언트가 토픽을 쓰는 동안(그 토픽으로 게시한 방이나 레코드, 목록, 구독. 새 토픽에 대한 `LIST_ROOMS`는 첫 참여를 최대 2초 기다림) 참여하고, 마지막 사용 10분 뒤에 떠나되 그 토픽으로 게시한 만료되지 않은 레코드나 구독한 클라이언트가 있으면 남습니다. 최대 256개 토픽.

**참여**: 서로 겹치지 않는 경로 3개로 저장 피어를 조회하고(테이블이 비었으면 아는 피어에게 물음), 각각에 `GET_TOPIC`을 보내고 응답의 토큰으로 `ANNOUNCE`합니다. 저장 피어는 알림을 10분 보관하며, 토픽당 멤버 최대 64개(새 멤버는 무작위 둘 중 오래된 쪽을 대신), 토픽 최대 2048개입니다. 멤버는 4분마다, 메시가 빈 동안은 30초마다 다시 알립니다. `GET_TOPIC`에는 저장 피어가 알림에서, 멤버가 아는 멤버에서 최대 16개를 도달 가능한 쪽부터 답합니다. 토큰(16바이트, `REGISTER`와 같음)이 묻는 쪽의 주소를 증명합니다.

**메시**: 멤버는 메시 이웃이 6개가 될 때까지 graft하고(도달 가능한 쪽부터. 토큰이 없으면 먼저 `GET_TOPIC`), 4개 아래면 더 graft하고, 12개를 넘으면 6개까지 prune합니다(먼저 자신을 graft한 이웃). 이웃 중 적어도 2개는 자신이 graft한 멤버입니다. 다른 쪽의 graft는 10개까지 받고, 자기 graft가 2개보다 적은 동안 graft합니다. 거부된 graft는 다른 멤버에게 갑니다. 60초 동안 소식이 없는 이웃은 빠지고, 30초 동안 트래픽이 없는 링크에는 빈 `IHAVE`를 보내 리프의 NAT 매핑을 열어 둡니다.

**가십**: 새 레코드는 즉시 모든 메시 이웃과 구독한 클라이언트에게 갑니다(`GOSSIP`). 5초 라운드마다 지난 라운드 이후 받은 ID는 이웃과 다른 도달 가능한 멤버 6개에게, 최근 두 라운드의 ID는 구독한 클라이언트에게 가며(`IHAVE`), 받는 쪽은 `IWANT`로 요청합니다. 새 이웃은 모든 ID를 받습니다. 레코드 ID는 `BLNK record 1\0`과 레코드 와이어 형식의 SHA-256 앞 16바이트입니다.

**레코드 확인**, 이 순서로:

1. 메시 이웃이나 요청을 받은 멤버에게서만.
2. 레코드 ID를 본 적 없음.
3. 토픽과 종류: 모드 토픽의 방, 채널 토픽의 채팅 줄, 플레이어 토픽의 접속 상태는 그 플레이어의 것만, 로그아웃은 그 플레이어 자신의 토픽에서만.
4. 시퀀스(오래된 것은 버림).
5. 서명.
6. 종류별 작성자 속도: 방 순간 8, 그 뒤 초당 1. 채팅 줄 순간 5, 그 뒤 초당 1, 5초보다 오래된 줄(기록)은 기록 허용량 32에서, 그 뒤 초당 1. 접속 상태와 로그아웃은 함께 순간 16, 그 뒤 5초당 1.
7. 표시 이름에 대한 작성자의 스탬프(접속 상태, 채팅 줄).
8. 만료와 수명: 방 저장소는 토픽당 512개, 호스트 키당 8개, 호스트 연결당 4개, 최대 600초 뒤. 커뮤니티 저장소는 접속 상태 256개, 연결마다 가장 새로운 것, 플레이어당 연결 최대 8개(그 이상의 연결은 먼저 만료되는 그 플레이어 연결의 자리를, 그 연결이 더 일찍 만료될 때만 차지), 최대 300초 뒤. 가장 새로운 채팅 줄 32개, 최대 30초 뒤의 날짜, 5분 보관. 플레이어마다 가장 새로운 로그아웃, 최대 300초 뒤, 최대 30초 뒤의 날짜.

실패는 모두 세고 벌점을 줍니다.

## 방 (`RoomAdvertisement`, `RoomDescription`, `RoomKey`)

**광고**(레코드 종류 1, 모드 토픽, 호스트가 서명): 플래그(1, 비트 0 철회), 토픽 키(33), 호스트 키(32), 호스트 연결(8), 방 번호(4), 시퀀스(4), 만료(에포크 ms, 8), 설명, 홈 피어(개수 1, 최대 3. 키 32 + 주소), 안정된 네트워크 좌표(플래그 1. `1`이면 16바이트가 뒤따름. 철회에는 없음), `Beacon.Link room advertisement 1\0`과 앞의 모든 바이트에 대한 호스트의 Ed25519 서명. 홈 피어와 좌표를 빼고 최대 545바이트(IPv6 항목 셋이면 716).

**설명**: 모드 지문(길이 바이트, 1~192바이트: 모드 id, 버전, 엔진 버전을 담은 모드 정체성의 와이어 형식), 방 이름과 맵 이름(텍스트, 각각 최대 48바이트, 방 이름은 비어 있지 않음), 플레이어 수와 정원(각 1. 플레이어 수는 정원 이하, 정원은 1 이상), 방 플래그(1: 비트 0 비공개, 비트 1 시작됨, 다른 비트 0), 참가 키(32, 비공개 방만), 모드 데이터(길이 바이트, 최대 64바이트, 그리고 바이트).

**모드 데이터**(`RoomSettings.getModData`): 모드가 정의하고 문서화하며, 피어와 클라이언트는 읽지 않고 나릅니다. 데모는 1바이트, 턴 속도를 게시합니다(`DemoLobby`).

**방 키**(`RoomKey`): 호스트 키 + 호스트 연결 + 방 번호. 더 높은 시퀀스가 낮은 것을 대신하고, 철회는 만료될 때까지 남습니다. 호스트는 40초마다 120초 만료로 갱신합니다. 피어는 토픽, 서명, 만료, 호스트 속도만 확인하고 토픽의 방을 나열합니다. 클라이언트는 자기 지문의 방과 모드의 다른 버전의 방(그 호스트가 줄 거부 사유와 함께)을 따로 나열하고, 모든 방의 모드 id와 버전을 보여 줍니다. 클라이언트의 모드 정체성이고, 플레이어 수가 정원보다 적고, 게임이 시작되지 않은 방에 참가할 수 있으며, 나머지는 닫힌 방입니다.

**비공개 방**: 광고에는 X25519 참가 키 쌍의 공개 절반이 담기고, 비밀번호는 보내지 않습니다. 참가자의 제안([신호](#신호-channelsignal))은 증명 = HMAC-SHA256(키 = 제안의 임시 키와 참가 키의 X25519 비밀, `SC4J Beacon.Link room password 1` || 호스트 키 || 방 번호(4) || 참가자 키 || 비밀번호 UTF-8)을 담습니다. 호스트는 개인 절반으로 비밀을 합의하고 틀린 증명을 거부합니다(`WRONG_PASSWORD`). 중계 노드는 비밀도 비밀번호도 모르며, 증명은 그 제안에만 맞습니다. 호스트와 공유하는 노드가 없는 참가자는 호스트의 홈 피어에 등록합니다(학습하거나 기억하지 않음).

## 커뮤니티 (`PresenceRecord`, `ChatLineRecord`, `SignOutRecord`, `SealedMessage`)

**접속 상태**(레코드 종류 2): 플래그(1, 0), 토픽 키(33), 플레이어 키(32), 연결 번호(8), 스탬프 nonce(8), 시퀀스(4), 만료(8), 표시 이름(텍스트, 최대 32. 스탬프가 묶는 이름), 모드 id(텍스트, 최대 48. 런처는 `sc4j-launcher`, `BeaconLink.LAUNCHER_MOD_ID`), 모드 버전(텍스트, 최대 24), 모드 지문 SHA-256의 앞 8바이트(함께 플레이할 수 있는 플레이어끼리 같음), 상태(1: `1` 대기 중, `2` 자리 비움, `3` 방에 있음, `4` 게임 중), 자리 비움 문구(텍스트, 최대 32, 자리 비움이 아니면 빈 값), 채널 이름(텍스트, 최대 32, 없으면 빈 값), X25519 귓속말 키(32, 세션마다), 홈 피어(방과 같음), 안정된 네트워크 좌표(방과 같음. 50초 갱신 때만 새로 함), `Beacon.Link presence 1\0`과 앞의 모든 바이트에 대한 서명.

- 모든 연결은 자기 접속 상태를 모드 토픽, 참가한 모든 채널, 플레이어 자신의 토픽에 게시하고, 120초 수명으로 50초마다 갱신하며, 바뀌면 바로 다시 서명하고, 채널을 떠나거나 닫을 때 5초 뒤 만료되는 접속 상태를 보냅니다. 오프라인으로 보이게 한 연결은 게시하지 않습니다(계정 전체 설정은 없음).
- 저장소와 클라이언트는 연결(키와 연결 번호)마다 가장 새로운 접속 상태를 보관합니다.
- **합친 접속 상태**(`ClientCommunity`): 보는 쪽이 따르는 토픽에 연결 중 하나라도 살아 있는 접속 상태가 있으면 온라인입니다. 순위가 가장 높은 연결이 상태, 모드, 자리 비움 문구를 정합니다: 게임 중, 방에 있음, 모드에서 온라인(런처가 아닌 곳에서 대기 중), 런처에 있음(모드 id `sc4j-launcher`로 대기 중), 자리 비움. 살아 있는 연결 수가 장치 수입니다. 사용자 목록은 각 플레이어를 한 번 보여 줍니다.
- **자기 플레이어 토픽**: 모든 연결이 구독하므로 계정의 다른 연결과 로그아웃을 봅니다.

**채팅 줄**(레코드 종류 3, 채널 토픽만): 플래그(1, 비트 0 감정 표현), 토픽 키(33), 작성자 키(32), 스탬프 nonce(8), 작성자 시퀀스(4), 타임스탬프(8), 표시 이름(텍스트, 최대 32), 텍스트(1~255바이트), `Beacon.Link chat line 1\0`과 앞의 모든 바이트에 대한 서명. 타임스탬프 5분 뒤 만료됩니다.

**토픽의 홈 피어**: 클라이언트가 처음 등록한 노드(최대 3개)가 그 토픽에 참여합니다.

- `PUBLISH_RECORD`(등록한 클라이언트 자신의 레코드)는 레코드를 그 토픽에 넣습니다. `RECENT`는 90초 동안 구독시키며(`RESULT` 값. 토픽당 구독자 최대 256), 3분의 1마다 갱신합니다. 기록 플래그가 있으면 피어는 먼저 가진 접속 상태, 채팅 기록, 로그아웃을 보냅니다.
- 피어는 새 레코드를 보내고(`GOSSIP`) 라운드마다 최근 두 라운드의 ID를 보내며(`IHAVE`), 구독자는 놓친 것을 `IWANT`로 받습니다. 클라이언트는 채팅을 위해 다른 클라이언트와 링크를 맺지 않습니다.
- `NOT_REGISTERED`로 거부된 줄은 토픽과 홈 피어마다 최대 8개 보관하고(가장 오래된 것이 자리를 내줌), 피어가 클라이언트를 다시 등록하면 순서대로 다시 게시합니다.
- 줄이 가는 길에서 라운드나 폴링 간격을 기다리는 곳은 없습니다.
- 클라이언트는 푸시된 레코드를 중계자처럼 확인하고(토픽, 종류, 만료, 스탬프, 서명) 본 레코드 ID는 버립니다. 작성자 속도는 홈 피어를 믿습니다.

**귓속말**(`SEALED`):

- 보낸 사람은 대상의 살아 있는 연결마다, 그 연결의 가장 새로운 접속 상태로 사본 하나를 봉인합니다. 새 키 쌍과 귓속말 키의 X25519 합의, HKDF-SHA256 일회용 키(솔트는 `SC4J Beacon.Link whisper 1`의 SHA-256, 두 플레이어 키와 두 X25519 키), 0 nonce와 두 플레이어 키를 연관 데이터로 한 타임스탬프(8)와 텍스트(최대 255)의 ChaCha20-Poly1305입니다.
- 서명된 사본은 대상 연결을 밝히고 그 연결의 홈 피어마다 가며, 전달되거나 모두 거부할 때까지 매초 최대 4번 다시 보냅니다. 그 등록을 가진 홈 피어는 바꾸지 않고 그 연결에만 전달하고 `DELIVERED`로, 아니면 `UNKNOWN_TARGET`으로 답합니다.
- 사본 하나가 전달되면 귓속말은 전달된 것이고(다른 사본도 계속 보냄), 모든 사본이 거부되거나 시도가 끝나면 오프라인입니다.
- 누구나 보낼 수 있으며(주소와 키 속도가 제한), 응답은 요청보다 길지 않습니다. 홈 피어는 보낸 사람, 대상, 크기만 보며, 오프라인 대상을 위해 저장하는 것은 없습니다.

**다른 곳에서 모두 로그아웃**(레코드 종류 4, `SignOutRecord`, `BeaconLinkSession.signOutOtherDevices`): 플래그(1, 0), 플레이어 자신의 토픽 키(33), 플레이어 키(32), 유지할 연결(8, 서명한 연결), 시퀀스(4), 타임스탬프(8, 에포크 ms), 만료(8, 타임스탬프 240초 뒤. 피어는 최대 300초 뒤까지 받음), `Beacon.Link sign out 1\0`과 앞의 모든 바이트에 대한 서명. 스탬프는 없습니다.

- 서명한 연결이 홈 피어를 통해 플레이어 자신의 토픽에 게시합니다(`PUBLISH_RECORD`. 나중에 그 연결을 등록하는 홈 피어도 받음).
- 자기 플레이어의 올바른 로그아웃이 다른 연결을 유지할 연결로 밝히고 타임스탬프가 자기 연결 시작보다 뒤이면, 연결은 `LinkFailure.SIGNED_OUT`으로 끝납니다. 채널을 닫고, 방을 철회하고, 떠나는 접속 상태를 보내고, 등록을 해제하고, 다시 등록하지 않습니다. 로그아웃을 가진 노드는 그것이 살아 있는 동안 그런 연결을 다음 갱신 때(150초 안에) 거부합니다. 타임스탬프 뒤에 시작한 연결은 영향을 받지 않습니다.
- 그 플레이어 토픽을 따르는 모든 클라이언트는 끝난 연결(유지할 연결이 아니면서 접속 상태 시퀀스(초)가 타임스탬프의 초 이하인 연결)의 접속 상태를 바로 버리고, 로그아웃이 살아 있는 동안 그 뒤의 접속 상태도 버립니다.
- 세션을 끝낼 뿐, 도난당한 키를 무효로 하지는 않습니다(새 계정이 필요합니다).

**무시 목록**(`CommunitySession.ignore`, `getIgnored`): 계정의 `blocked.json`([파일](#파일). 게스트는 메모리). 무시한 플레이어의 줄과 귓속말은 전달하지 않고, 모드가 그 방을 숨깁니다. 네트워크로는 아무것도 가지 않습니다.

## 네트워크 좌표 (`NetworkCoordinate`, `CoordinateReport`, `CoordinateEstimator`)

3차원과 높이를 쓰는 Vivaldi입니다. 두 호스트의 추정 왕복 시간은 두 점의 거리와 두 높이의 합입니다.

- **좌표**: 16바이트. 세 성분과 높이, 각각 부호 있는 32비트 정수 밀리초(성분은 원점에서 10,000 ms 이내, 높이는 0~10,000 ms. 그 밖은 가장 작은 int를 포함해 거부).
- **보고**: 좌표와 오차(1바이트, 100분의 1 단위, 최대 150. 아무것도 모르는 호스트는 1.5). 카드(`HELLO`, `FIND_PEERS`, `DIAL_BACK`, `ANNOUNCE`, `GRAFT`), `PEERS`, `OBSERVED_ADDRESS`가 보낸 쪽의 보고를 담으며, 좌표만을 위한 메시지는 없습니다.
- **표본**: 피어는 `HELLO` 요청(후보와 조용한 피어에게)과 조회 요청의 왕복 시간을 응답의 보고와 함께 잽니다. 클라이언트는 재전송하지 않은 노드 요청에 답이 오면 왕복 시간을 재고, 그 노드의 마지막 `OBSERVED_ADDRESS`나 `PEERS`의 보고를 씁니다. 런타임 세션과 내장 피어는 추정기 하나를 함께 씁니다.
- **갱신**: 표본은 측정 시간과 추정 시간의 차이에, 두 오차 중 자기 오차의 비율과 0.25를 곱한 만큼 좌표를 옮기고, 오차도 같은 가중치로 표본의 상대 오차를 따라갑니다. 높이는 0.1 ms 이상, 5초를 넘는 표본은 무시, 원점으로 약하게 당깁니다. 원격 호스트당 5분에 표본 하나(최근 64개 기억).
- **안정**: 서로 다른 호스트 6개의 표본으로 오차가 0.6 이하가 되면 안정됩니다. 안정된 좌표만 방과 접속 상태에 들어가며, `LatencyEstimate`(100 ms까지 good, 200 ms까지 fair, 그 위 poor)는 어느 쪽이든 좌표가 없으면 알 수 없음입니다.
- **이상값**: 안정된 좌표는 측정 시간과 추정 시간이 4배보다 더 차이 나는 표본을 거부하고(피어는 `COORDINATE_OUTLIER`와 벌점 1점), 그런 표본이 연달아 오면 8번째마다 받아들여, 옮겨 간 호스트의 오차가 커져 안정이 풀립니다.
- **개인 정보**: 좌표는 지연 공간의 정수 밀리초만 알리고 주소는 담지 않습니다. 오프라인으로 보이는 플레이어는 좌표를 게시하지 않고, 방의 좌표는 호스트의 것입니다.

## 참가자 사이의 채널 (`sc4j-beaconlink`, `channel` 패키지)

### 신호 (`ChannelSignal`)

`SIGNAL` 페이로드는 종류(1), 보낸 쪽의 연결 번호(8), 필드입니다. 서명된 보낸 쪽 키와 그 연결이 보낸 참가자이고, `SIGNAL`은 대상 키와 연결을 밝힙니다. 따라서 참가 요청은 보내는 호스트 연결과 제안의 방 번호로 방을 가리킵니다. 주소 후보는 개수(1, 최대 8)와 주소입니다. 클라이언트는 공유기의 포트 매핑이 있으면 그 주소를 맨 앞에, 다음에 노드가 관찰한 주소, 그다음 로컬 주소를 둡니다.

| 종류 | 보낸 쪽 연결 뒤의 필드 |
|---|---|
| `1` OFFER | 시작하는 쪽의 수신 번호(8), X25519 임시 공개 키(32), 참가 플래그(1). 플래그가 `1`이면 방 번호(4), 참가자의 모드 정체성(길이 바이트와 바이트), 비공개 방의 비밀번호 증명(길이 바이트 `0` 또는 `32`와 바이트. [방](#방-roomadvertisement-roomdescription-roomkey) 절). 그 뒤 후보 |
| `2` ANSWER | 시작하는 쪽의 수신 번호(8), 응답하는 쪽의 수신 번호(8), 임시 공개 키(32), 후보 |
| `3` REFUSAL | 시작하는 쪽의 수신 번호(8), 사유(1): `0` 호스트가 그 방을 가지고 있지 않음, 그 밖은 엔진 `JoinRefusal`의 코드(엔진 버전, 모드 정체성, 꽉 찬 방, `9` 틀린 비밀번호) |

두 임시 키와 수신 번호는 두 정체성으로 인증됩니다. 키가 낮은 참가자가 제안하고, 계정 하나의 두 연결 사이에서는 연결 번호가 낮은 쪽이 제안하며(둘 다 부호 없이 비교), 참가자는 항상 제안합니다. 호스트는 아직 연결되지 않은 참가를 최대 16개 보관하며, 새것이 가장 오래된 것을 대신합니다.

### 키 스케줄 (`ChannelKeys`)

- transcript = SHA-256(`SC4J Beacon.Link channel 1` || 시작하는 쪽 정체성 || 시작하는 쪽 연결 || 응답하는 쪽 정체성 || 응답하는 쪽 연결 || 시작하는 쪽 임시 키 || 응답하는 쪽 임시 키 || 시작하는 쪽 수신 번호 || 응답하는 쪽 수신 번호)
- PRK = HMAC-SHA256(key = transcript, X25519 비밀)
- key(시작하는 쪽 -> 응답하는 쪽) = HMAC-SHA256(PRK, `initiator to responder` || 0x01)
- key(응답하는 쪽 -> 시작하는 쪽) = HMAC-SHA256(PRK, `responder to initiator` || 0x01)

모두 0인 비밀은 거부하고, 비밀은 쓴 뒤 0으로 지웁니다.

### 데이터그램 (`ChannelDatagramUtils`, `ChannelCipher`, `ChannelFrame`)

`BLCH`(4) | 받는 쪽의 수신 번호(8) | 카운터(8) | 프레임의 ChaCha20-Poly1305 암호문 | 태그(16). 최대 1200바이트. 연관 데이터는 헤더 20바이트, nonce는 0 바이트 4개와 카운터입니다. 카운터는 방향마다 0부터 시작하고, 256 카운터 재전송 창을 복호화 전에 확인하고 인증 뒤에 기록합니다. 채널 데이터그램은 클라이언트의 UDP 소켓을 엔벨로프와 함께 쓰며 매직으로 구별합니다.

**프레임 타입**(`ChannelFrameType`): `1` PROBE, `2` PROBE_ACK(홀 펀칭), `3` DATA(최대 1024바이트), `4` PING, `5` PONG(2.5초마다 연결 유지, 지연), `6` CLOSE, `7` RELAY_QUERY, `8` RELAY_STATUS, `9` RELAY_FORWARD, `10` RELAY_DELIVER. 중계 프레임은 상대 참가자를 와이어 형식(40바이트)으로 밝힙니다. 직접 경로가 없는 쌍은 양쪽과 직접 채널이 있고 측정 지연이 가장 낮은 참가자를 거쳐 중계합니다. A가 C에게 RELAY_FORWARD(B, 봉인된 A->B 데이터그램)를 보내면 C가 B에게 RELAY_DELIVER(A, 같은 바이트)를 보냅니다. 중계자는 이를 읽거나 바꿀 수 없고 쌍마다 정해진 양까지만 나릅니다. 피어는 자신이 참여하지 않은 게임의 채널 데이터그램을 중계하지 않습니다.

### 오버레이 (`LinkOverlay`, `ChannelOverlay`)

오버레이 데이터그램은 포트 바이트와 최대 1023바이트이며 참가자 단위로 주소를 정합니다. 포트 1~15는 엔진의 것입니다: `1` 엔진 로비(참가자 목록이 각 멤버의 참가자를 와이어 형식으로 밝힘), `2` 엔진 락스텝 전송. 포트 16~255(`LinkOverlay.FIRST_MOD_PORT`)는 모드 자체의 프로토콜용이며, 모드가 문서화합니다.

## 파일

공유 파일(`SharedFile`)은 여러 프로세스(런처의 노드, 게임, 자기 폴더의 헤드리스 노드)가 함께 씁니다. 쓰는 쪽은 파일을 읽기/쓰기로 열고, 배타 잠금을 잡고, 읽고, 자기 변경을 병합하고, 결과를 제자리에 쓰고, 나머지를 잘라 내고, 디스크에 강제로 쓰고, 잠금을 풉니다. 읽는 쪽은 공유 잠금을 잡습니다. 이름 바꾸기, 임시 파일, 백업 파일은 없습니다. 없거나 빈 파일은 아무것도 담지 않고, 손상된 파일은 경고 한 번과 함께 빈 것으로 보고 다음 병합이 다시 씁니다. 각 프로세스는 병합 결과를 자기 뷰로 삼습니다.

| 파일 | 내용 |
|---|---|
| `<install>/launcher/seeds.json` | 함께 배포되는 시드 목록, 릴리즈마다 바뀜. `nodes.json`과 같은 형식 |
| `<install>/userdata/beaconlink/nodes.json` | 사용자의 노드 목록(`NodeListFile`). 사용자가 저장할 때 쓰고 `--seeds`로 넘김. 없는 동안은 `seeds.json`이 대신함. `{"format": 1, "nodes": [...]}`, 항목은 `"host:port"`(어느 키든) 또는 `{"address": "host:port", "key": "<64 hex digits>"}`(고정 키). 최대 64 KiB, 중첩 최대 8, IPv6 호스트는 대괄호 |
| `<install>/userdata/beaconlink/node.json` | 런처 Beacon.Link 설정 `{"format": 1, "role": "automatic", "port": 7455, "portMapping": true}`. `automatic`(포트에서 수신, 자체 시험을 통과하면 전체 피어) 또는 `off`(빈 포트에서 리프 전용). `portMapping`(선택, 기본값 `true`): 공유기에 노드와 게임의 포트를 열어 달라고 요청. 없으면 7455에서 자동, 포트 매핑 켬 |
| `<install>/userdata/beaconlink/peers.json`, 노드의 `<state>/peers.json` | 학습한 피어(`PeerStore`, 공유 파일), 아래 |
| `<install>/userdata/beaconlink/peer.key`, 노드의 `<state>/identity.key` | 키 파일. 증명 nonce는 시작할 때마다 다시 찾음 |
| `<install>/userdata/beaconlink/node.lock` | 빈 파일. 노드를 실행하는 런처가 잠금 |
| `<install>/userdata/beaconlink/accounts/<id>/` | 계정([정체성](#정체성)), 아래 |

**`peers.json`**: `{"format": 1, "peers": [{"key": "<hex>", "address": "<IP literal>", "port": <port>, "firstSeen": <ms>, "lastSuccess": <ms>, "failures": <n>}, ...]}`, 최대 256개, 최대 256 KiB. `lastSuccess` 0은 알려졌지만 답한 적 없는 피어입니다. 병합: 키 기준 합집합. 같은 키는 더 새로운 `lastSuccess`가 주소, 포트, 실패 수를 정하고(같으면 더 큰 `failures`), `firstSeen`은 최솟값. 한 주소의 두 키는 더 새로운 `lastSuccess`가 남음. 실패 3번이거나 30일보다 오래된 항목(`lastSuccess`, 답한 적 없으면 `firstSeen`)은 버림. `lastSuccess` 내림차순, `firstSeen` 오름차순, 키 오름차순으로 256개에서 자름. 프로세스는 마지막 병합 이후 자기가 바꾼 항목만 5분마다와 멈출 때 병합하며, 리프는 쓰지 않습니다.

**계정 폴더**: `identity.key`(플레이어 키). `account.json` `{"format": 1, "name": "<name>", "difficulty": 24, "stamp": <nonce>, "lastUsed": <epoch ms>}`(스탬프가 이름을 묶지 않는 폴더는 계정이 아님). `friends.json`(`PlayerListStore`, 공유 파일: `{"format": 1, "players": [{"key": "<hex>", "time": <ms>, "removed": false}, ...]}`. 키마다 가장 새로운 `time`이 이기고, 같으면 삭제. 삭제는 30일 남음. 최대 16명, 오래된 추가부터 밀려남. 자기 변경마다 병합, 10초마다 다시 읽음). `blocked.json`(무시한 플레이어, 같은 형식과 규칙, 최대 256명). `account.lock`(빈 파일, 계정을 쓰는 모든 프로세스가 공유 잠금).

토픽, 알림, 메시, 레코드, 등록, 구독, 귓속말 키, 벌점, 그레이리스트는 메모리에만 있습니다.

## 버전 관리

프로토콜 1이 유일한 프로토콜입니다. 받는 쪽은 버전 바이트가 다른 엔벨로프를 버리고, 모르는 종류와 기능 비트는 버리거나 무시합니다. 1.0 전에는 프로토콜 번호, 레코드와 파일 버전, 해시와 서명 도메인의 번호가 모두 `1`이고, 구조는 번호를 바꾸지 않고 바뀔 수 있습니다. 피어는 `HELLO`와 `PONG`에 소프트웨어 버전을 보내며(`MeshPeer.SOFTWARE`, `sc4j-beaconlink-peer 0.11`), 이 값에 의존하는 규칙은 없습니다.

피어 계층은 IPv4만 라우팅합니다. 런타임의 세션 소켓(`UdpDatagramEndpoint`)이 IPv4이고, 프로세스는 소켓 하나를 씁니다(관찰된 주소가 홀 펀칭 주소여야 함). IPv6 `PEERS` 항목은 버리고 IPv6 시드에는 닿지 않습니다. 주소 인코딩과 /48, /32 한계는 IPv6를 다룹니다.
